httpp has no ASGI or WSGI layer. It is the server and the framework in one, so a handler is called by the engine itself, with nothing in between. This page says what that means, why it is faster, and what you give up.

## What is not there

- **The interfaces.** There is no `environ` / `start_response` (WSGI) and no `scope` / `receive` / `send` (ASGI). `httpp.Server` is not an ASGI app, so `uvicorn main:app` does not start it: you start it with `httpp py run main:app` or `app.listen(...)`.
- **A separate server process.** There is no uvicorn or gunicorn under your app. Sockets, HTTP parsing, keep-alive, timeouts and TLS are the library's own C++ engine.
- **Third-party ASGI middleware.** `add_middleware()` takes the classes of `httpp.middleware` only and raises `TypeError` for anything else. An ASGI app cannot be mounted inside a server, and a server cannot be mounted in one.

## What takes their place

The two ideas behind the standards are still there, in a simpler form.

So a decorator and a function are all you write, and the same server runs both kinds of handler. A C++ handler is called directly, with the same hooks.

## Why this is faster

This design is one reason httpp is fast: it is faster than bare ASGI on uvicorn, which is the floor for what an ASGI server can do, and many times faster than FastAPI on top of it. How much of the gain comes from the missing ASGI layer is not known (see the note below).

In the usual stack (FastAPI on Starlette on uvicorn on a socket) every layer boundary costs something: a copy of the data, a hop to another thread, or time under the GIL. Making one layer fast leaves the boundaries. httpp owns both the top and the bottom, so a request goes from the socket to your handler without being translated into an ASGI `scope` and back.

It also decided what is left out. A middleware stack wraps every request in extra calls and, in Python, extra frames. httpp has `before_request`, `after_request` and the error handlers instead, and the jobs people write middleware for are core features (compression is `set_compression` in C++ and `GZipMiddleware` in Python, and CORS, trusted hosts and the HTTPS redirect are classes of `httpp.middleware`). Handlers that do not ask for a `request` never get one built.

What the measurements say. The numbers are from the published run on the [Benchmarks](benchmarks.mdx) page (CPython 3.14, a laptop with a Core i7-13620H, the server on 8 CPUs and the load generator on 8 others, 64 connections), against one bare uvicorn worker:

- With one I/O thread, the like-for-like setting against one uvicorn event loop, `def` and `async def` routes did 2.8 to 3.3 times the requests per second of bare uvicorn (an ASGI function with no routing and no validation) on `hello` (a constant answer) and `json` (a path parameter and a JSON body), and 11 to 15 times FastAPI on uvicorn, on both the GIL and the free-threaded build. With more I/O threads `hello` reached 7.3 times (GIL) and 7.7 times (free-threaded) bare uvicorn.
- A CPU-bound `def` handler (about 60 µs of work) did 23 to 24 thousand requests per second on the GIL build and 58 to 71 thousand on the free-threaded build, against 20 and 18 thousand for bare uvicorn.

:::note

These numbers compare whole stacks. No run changes only the ASGI part, for example by putting an ASGI adapter on the same engine, so how much of the gain is the missing ASGI layer, and how much is the C++ engine, the thread pool and the routing, has **not been measured**. Numbers from different runs or machines are not comparable, so only comparisons inside one run mean anything.

:::

## What you give up

- You cannot run an existing ASGI or WSGI app on httpp, or use middleware written for ASGI (Sentry's or OpenTelemetry's ASGI middleware, for instance). Use their client libraries from a hook instead.
- A FastAPI app is not drop-in. The names are the same (`Query`, `Depends`, `HTTPException`, `response_model`, `/docs`), so most code moves by changing the import, but the middleware stack and the Pydantic models are httpp's own.
- A blocking call inside an `async def` handler blocks every async request on its loop: all of them with the GIL, where there is one loop, and those of the same I/O thread on a free-threaded Python. Use a plain `def` handler for blocking work.

## Later

An ASGI adapter, to run third-party ASGI apps on the engine, is on the list with low priority. It would bring the boundary back for those apps, and translating `scope`, `receive` and `send` would limit their speed, so it is only for someone who needs a third-party app and is not part of the plan for your own code.
